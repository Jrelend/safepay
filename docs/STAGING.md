# SafePay Beta v0.1 — private staging

> **Simulation only.** Staging never collects, holds or moves real money, has no
> bank/card/QPay integration, and refuses to start if a real-payment mode is set
> (`PAYMENT_MODE` must be `simulation`; `PAYMENTS_SIMULATION_ONLY` must be `true`).
> Use test data only. **Nothing in this document has been deployed yet.**

## Architecture

```
 tester's browser
      │ HTTPS only (80 → 308 redirect)
      ▼
 ┌──────────────── VPS (Docker Compose: compose.staging.yaml) ────────────────┐
 │  caddy  ── the ONLY published service (80/443)                              │
 │    • TLS (Let's Encrypt, or Caddy's internal CA)                            │
 │    • IP allow-list (ALLOWED_IPS) + stricter admin allow-list                │
 │      (ADMIN_ALLOWED_IPS for /admin, /api/admin)                             │
 │    • HTTP basic auth (one shared beta login)                                │
 │    • HSTS, CSP, X-Frame-Options, Referrer-Policy; no access log             │
 │    • drops the Authorization header; sets X-Forwarded-For = real client IP  │
 │        │  network "frontend" (internal: no internet)                        │
 │        ▼                                                                    │
 │  web (Next.js) ── /api/*        → api       (FastAPI, safepay_app)          │
 │                └─ /api/admin/*  → admin-api (FastAPI, safepay_admin)        │
 │                                      │ network "backend" (internal)         │
 │                                      ▼                                      │
 │  db (PostgreSQL 17, volume pgdata) ◀── worker (safepay_system)              │
 │                                    ◀── migrate (one-shot, safepay_migrator) │
 └─────────────────────────────────────────────────────────────────────────────┘
```

| Control | How |
|---|---|
| HTTPS only | Caddy redirects 80 → 443; HSTS (1 year); session cookies are `__Host-…; Secure; HttpOnly` (admin cookies `SameSite=Strict`) |
| Private access | IP allow-list + shared basic auth at the edge, then the app's own login; admins additionally need an admin password + TOTP and an allow-listed IP |
| No exposed internals | Only `caddy` publishes ports. `db`, `api`, `admin-api`, `web`, `worker` are on `internal: true` networks (no internet egress either). CI asserts this. |
| Separate DB credentials | Five roles: superuser (init only), `safepay_migrator` (migrations, owner CLI), `safepay_app`, `safepay_system`, `safepay_admin`. Each container gets only its own. |
| Secrets | `.env.staging` generated by `scripts/staging-init-secrets.sh` (random 192-bit passwords, bcrypt basic-auth hash), `chmod 600`, git-ignored. Never commit it; keep an encrypted copy in a password manager. |
| Hardening | Read-only root filesystems (tmpfs `/tmp`), `cap_drop: ALL` (+ only what PostgreSQL/Caddy need), `no-new-privileges` |
| Health checks | db (`pg_isready`), api/admin-api (`/health`), web (`/`), caddy (internal `/healthz`); `migrate` must exit 0 before apps start |
| Resource limits | db 1 GB/1 CPU · api 512 MB/1 CPU · web 512 MB/1 CPU · admin-api 256 MB · migrate 256 MB · worker 192 MB · caddy 128 MB |
| Restart policy | `unless-stopped` (migrate: `no`) |
| Log rotation | Docker `json-file`, 10 MB × 5 files per container; the API logs one redacted line per request (invite tokens and query strings never logged) |
| Backups | `scripts/staging-backup.sh`: verified `pg_dump` (custom format), SHA-256, optional `age` encryption, 14 daily + 8 weekly retention |
| Release safety | Automatic release is OFF (`platform_policy`), enforced in SQL; worker `WORKER_AUTO_RELEASE=false` |

## Requirements

### Server (minimum practical for 10–30 testers)

| Resource | Minimum | Why |
|---|---|---|
| CPU | 2 vCPU (shared is fine) | Next.js + 2 uvicorn workers + PostgreSQL; idle most of the time |
| RAM | **4 GB** | Container limits add up to ~2.6 GB, plus the OS, Docker and image builds. 2 GB works only if images are built elsewhere. |
| Disk | 40 GB SSD | OS + Docker images (~3 GB) + database (< 1 GB for a 30-person beta; evidence files ≤ 2 MB each, capped per dispute) + local backups (< 2 GB) |
| OS | Ubuntu 24.04 LTS (or Debian 12) | Docker Engine + Compose v2 plugin |
| Network | Public IPv4, ports 80/443 open; SSH restricted to your IP | |

Measured locally: the API, admin API and web containers each idle well under their
limits. The database for this beta is tiny (a full dump is ~130 KB without user data).

### Domain and DNS
* One hostname, e.g. `staging.example.mn` (an existing domain's subdomain is enough).
* `A` (and optionally `AAAA`) record → the VPS IP.
* For a trusted certificate set `CADDY_TLS` to an email address (Let's Encrypt via
  HTTP-01 on port 80). Without a public DNS name, use `CADDY_TLS=internal` and accept
  the browser warning (testers must trust Caddy's root CA or click through).

### Email
* Beta v0.1 sends **no real email**: verification and password-reset links go to the
  `email_outbox` table. On staging the operator reads them with the owner CLI and
  passes them to the tester over a trusted channel:
  `docker compose ... run --rm migrate python -m app.cli outbox tester@example.mn`
* Before a wider beta: add a transactional provider (Amazon SES, Postmark, Resend…)
  with SPF, DKIM and DMARC on the sending domain.

## Deployment instructions (for later — do not run until approved)

1. **Provision** a VPS (Ubuntu 24.04, 2 vCPU, 4 GB). Create a non-root sudo user,
   disable password SSH, allow only your IP on port 22, and open 80/443:
   ```bash
   sudo ufw default deny incoming && sudo ufw allow from <your-ip> to any port 22 \
     && sudo ufw allow 80,443/tcp && sudo ufw enable
   ```
2. **Install Docker** Engine and the Compose plugin (docs.docker.com/engine/install/ubuntu),
   and `age` if you want encrypted backups: `sudo apt install age`.
3. **Get the code** (a reviewed, tagged commit):
   ```bash
   git clone https://github.com/Jrelend/safepay.git && cd safepay && git checkout <tag>
   ```
4. **Create secrets** (prints the basic-auth password once — save it):
   ```bash
   scripts/staging-init-secrets.sh staging.example.mn
   ```
   Then edit `.env.staging`:
   * `ALLOWED_IPS` — testers' networks (or `"0.0.0.0/0 ::/0"` if you rely on basic auth);
   * `ADMIN_ALLOWED_IPS` — only your office/VPN address(es);
   * `CADDY_TLS` — your email for Let's Encrypt (DNS must already point at the VPS);
   * optionally `BACKUP_AGE_RECIPIENT` (an `age` public key).
5. **Start**:
   ```bash
   docker compose -f compose.staging.yaml --env-file .env.staging up -d --build
   scripts/staging-wait.sh
   ```
6. **Smoke check** from your machine: `https://staging.example.mn` asks for the basic-auth
   login, then shows the Mongolian landing page with the simulation banner;
   `http://` redirects to `https://`; `https://…/api/health` is 404 (internal only).
7. **Create the first admin.** Register normally in the browser, get the verification
   link, verify, then grant admin rights (asks for a SEPARATE admin password and prints a
   TOTP secret once — add it to an authenticator app):
   ```bash
   dc() { docker compose -f compose.staging.yaml --env-file .env.staging "$@"; }
   dc run --rm migrate python -m app.cli outbox you@example.mn
   dc run --rm -it migrate python -m app.cli grant-admin you@example.mn --note "staging admin"
   ```
   Sign in at `https://staging.example.mn/admin/login` from an allow-listed IP.
8. **Backups**: run once by hand, then schedule (root crontab, 02:15 daily):
   ```bash
   scripts/staging-backup.sh
   15 2 * * * cd /home/deploy/safepay && scripts/staging-backup.sh >> backups/backup.log 2>&1
   ```
   Copy `backups/` off the server (e.g. `rclone sync backups/ b2:safepay-staging-backups`).
   **Test a restore** before inviting testers (see below).
9. **Invite testers**: share the URL and the basic-auth login over a private channel;
   relay verification links with the `outbox` command until real email exists.

### Restore
```bash
scripts/staging-backup.sh                       # safety copy of the current state first
scripts/staging-restore.sh backups/daily/safepay-<timestamp>.dump      # asks to confirm
# encrypted: AGE_IDENTITY_FILE=~/age-key.txt scripts/staging-restore.sh <file>.dump.age
```
The restore checks the SHA-256, stops the app containers, recreates the database,
re-applies the role bootstrap, restores in one transaction, checks ownership, and starts
everything again (`migrate` then brings the schema to the code's head).

### Update to a new reviewed version
```bash
scripts/staging-backup.sh
git fetch && git checkout <new-tag>
docker compose -f compose.staging.yaml --env-file .env.staging up -d --build
scripts/staging-wait.sh
```
Rollback: check out the previous tag and restore the pre-update backup (migrations may
not be downgradable once data exists — they refuse to destroy data).

### Operations
* Logs: `docker compose -f compose.staging.yaml --env-file .env.staging logs -f api worker`
* Worker: logs `automatic release: disabled` at start and one line per pass.
* Rotate a DB role password: change it in `.env.staging`, run
  `ALTER ROLE … PASSWORD …` as the superuser (`dc exec db psql -U postgres`), restart.
* Suspend a user: admin UI → Хэрэглэгчид. Revoke an admin: `app.cli revoke-admin`.
* Tear down (destroys data): `docker compose … down -v`.
